1. NOVAAI MARKET's data-processing model

NOVAAI MARKET is operated as a South African sole proprietorship by Thabiso Putlane. The platform uses third-party service providers for database, authentication, storage, backend hosting and AI inference.

Personal information in the marketplace may include buyer and seller names, cellphone numbers and email addresses; seller public-area/location information; account and authentication data; listing content and communications supplied by users. The platform's AI backend is not designed to attach complete buyer or seller profile records to Groq prompts.

The previously inspected AI flow sends the current user message and up to eight prior conversation messages from the browser to the Render backend. Render validates the Supabase bearer token. The backend then sends system instructions, conversation history and the current message to Groq. The reviewed code does not show the Supabase bearer token being forwarded to Groq or deliberate attachment of account profile fields. Users may nevertheless include personal information in messages.

The inspected AI application does not save chat histories in NOVAAI MARKET's application database; browser conversation context is temporary and clears on refresh. This does not mean providers retain no technical metadata.

4. POPIA section 72 — international transfers

Section 72 restricts transfers of personal information to a third party in a foreign country unless one of the statutory conditions is met. Relevant routes include an adequate level of protection through law, binding corporate rules or an agreement providing substantially similar protection and addressing onward transfers; informed consent; qualifying contractual necessity; or another applicable statutory condition.

NOVAAI's assessment does not assume that a provider's European location or the existence of EU Standard Contractual Clauses automatically proves compliance with section 72. The relevant transfer condition must be identified for each recipient and onward recipient, and the applicable safeguards and evidence retained.

5. Provider retention, backups and deletion assessment

Supabase

Supabase publishes plan-dependent database backup information. Its documentation distinguishes database backups from Storage objects; Storage objects are not included in database backups. Backup availability and retention depend on the subscribed plan and configuration. The actual NOVAAI plan, backup status, backup lifecycle and account-specific deletion completion have not been independently confirmed in this assessment.

Control: identify the actual plan and enabled backup features in the account records; document database backup retention separately from Storage object retention; use the provider's deletion process; and retain provider confirmation where available. Do not assume deleting a database row removes an object or every backup copy.

Render

Render documents ephemeral service filesystems and separate persistent-disk and Postgres backup arrangements. The NOVAAI AI backend is a Render service and the previously inspected application code does not persist conversation histories in an application database. This does not establish that Render retains no logs, metadata or infrastructure copies.

Control: document the service's actual disk configuration and applicable log/metadata retention; distinguish service filesystem behaviour from platform logs and any separately provisioned database; and obtain the applicable deletion and backup lifecycle confirmation.

Groq

Groq's data-controls documentation describes inference input/output retention, usage metadata, reliability and abuse-monitoring records, and separate Batch and fine-tuning data handling. The previously reviewed account screenshot showed Inference API ZDR enabled. The inspected NOVAAI backend uses the Chat Completions inference endpoint and does not use Batch or fine-tuning endpoints.

Control: retain the inference ZDR setting evidence; do not describe ZDR as eliminating all usage metadata; keep Batch and fine-tuning disabled or unused for this workflow; and obtain account-specific confirmation of metadata retention, deletion and applicable subprocessors.

No deletion certification is claimed: This page records the provider policy review and NOVAAI controls. NOVAAI has not received provider-issued deletion certificates or account-specific written backup-retention confirmations as part of this assessment. 6. NOVAAI controls and operating commitments

  1. Use only the personal information reasonably necessary for each marketplace and AI purpose.
  2. Do not deliberately include buyer or seller profile fields, private contact details or private street-level location information in Groq prompts.
  3. Keep product/listing search data distinct from private account and authentication data.
  4. Maintain access controls, authentication checks and least-privilege access to provider dashboards.
  5. Keep the current DPA, applicable account terms, subprocessor disclosures, transfer safeguards and account-setting evidence in the internal compliance record.
  6. Review provider changes, new subprocessors, new processing countries and material changes to AI data flows before relying on them.
  7. Record provider deletion requests and responses. Do not promise immediate removal from backups unless the provider confirms the applicable lifecycle.
  8. Review this assessment at least annually and whenever a provider, data category, processing purpose, location or material service configuration changes.
